Amend the existing AI PDF chat feature in Avalanche (repo: https://github.com/etb190/Avalanche, code in Features/AI/) so it works against a locally installed Ollama, using the cloud model "gpt-oss:120b-cloud" for chat.

DO NOT rebuild the feature. DO NOT redesign the sidebar. DO NOT touch normal PDF search. Keep the provider abstraction (IAiProvider, IEmbeddingProvider). Read the existing code first, then make targeted changes.

==================================================
1. WHAT OLLAMA IS AND HOW IT BEHAVES
==================================================

Ollama is already installed on this machine. It runs a local HTTP server at http://localhost:11434 (loopback only by default). The desktop app or `ollama serve` starts it.

- Cloud models: model names ending in "-cloud" (here "gpt-oss:120b-cloud") are not run locally. The local Ollama server forwards the request to ollama.com and streams the reply back. The user must be signed in once with `ollama signin`. Our app only ever talks to localhost.
- Auth: the local server needs NO API key. OpenAI-style clients still need a non-empty string, so use a dummy like "ollama". The app must NOT refuse to run because the key is empty when the base URL is localhost.
- Free account limits: 1 concurrent cloud request; extra requests queue and may be rejected when the queue is full; there is a small usage allowance that can run out. So: never send two chat requests at once, and handle rejection/limit errors gracefully.
- Cloud data handling: with a "-cloud" model the user's questions and the retrieved PDF passages leave the machine (sent to ollama.com). Avalanche promises documents stay on the computer, so the settings UI must show a short, visible notice when the selected chat model ends in "-cloud" or the base URL is not localhost. Use the existing localization resource pattern (Strings/ dictionaries) for all new text; the repo has a localization gate that rejects hardcoded UI strings.

Endpoints (all on http://localhost:11434):
- OpenAI-compatible: POST /v1/chat/completions, POST /v1/embeddings, GET /v1/models
- Native: POST /api/chat, POST /api/embed, GET /api/tags (lists installed models), GET /api/version
- We use the /v1 endpoints for chat and embeddings (keeps the existing OpenAI-compatible provider). Use GET /api/version (or /api/tags) only as a cheap "is Ollama running" health check.

Chat model: "gpt-oss:120b-cloud". Exact string, configurable, never hard-coded outside the default settings value.

gpt-oss is a REASONING model. Consequences:
- The response message may include a separate "reasoning" field in addition to "content". Ignore it for display; never show it and never log it.
- Reasoning tokens count against max_tokens. With the current default MaxTokens=2000, content can come back empty or truncated. Raise the default max_tokens to at least 4096 (configurable) and treat an empty "content" with finish_reason "length" as a specific, friendly error ("Answer was cut off; try a shorter question or raise the token limit"), not a crash.
- Optionally support a "reasoning_effort" setting (low/medium/high, default "low" or "medium" for Q&A speed) passed on the /v1 request. Verify empirically that the endpoint accepts it; if it errors, omit it and fall back silently.
- Temperature: 0.1-0.3.
- Structured output: try response_format {"type":"json_object"} first (or a json_schema if it works reliably with this model). Regardless, the parser MUST tolerate: markdown code fences around JSON, leading/trailing prose, and missing fields. If JSON parsing fails, show the raw text as the answer with no source buttons rather than throwing.
- Set HttpClient.Timeout to 300 seconds for chat (cloud + reasoning can be slow). Support cancellation via the existing CancellationToken/cancel UI. Streaming is optional; do not add it unless it is simple.

Embeddings are a SEPARATE model. gpt-oss cannot produce embeddings. Use a local embedding model via the same Ollama server:
- Default embedding model: "nomic-embed-text" (user must run `ollama pull nomic-embed-text` once). Also allow "mxbai-embed-large" via config.
- Endpoint: POST /v1/embeddings with {"model": "...", "input": ["text1","text2",...]}. Response: data[i].embedding, in order.
- nomic-embed-text works best with task prefixes: prepend "search_document: " to chunk texts when indexing and "search_query: " to the user question when retrieving. Make the prefixes part of the embedding provider config (empty for models that don't want them).
- Keep chunk text under roughly 1,200 characters for embedding (Ollama's default context for this model is small); truncate defensively.
- Different embedding models have different vector sizes. Store the embedding model name and dimension in the index metadata. If the configured model or dimension differs from what an existing index was built with, discard and rebuild that index. Never mix vectors from two models.
- If the embedding model is not installed, Ollama returns a 404-style "model not found" error. Map it to: "Embedding model not found. Run: ollama pull nomic-embed-text".
- Embeddings must stay local (nomic-embed-text, no -cloud suffix) so indexing does not consume the free cloud allowance and PDF text is not sent to the cloud during indexing.

3. BUGS IN THE EXISTING CODE THAT MUST BE FIXED (they will break Ollama results too)
==================================================

1. Source IDs do not match. The prompt tells the model to cite "SOURCE_0"-style IDs, but NavigateToSource looks up chunks by ChunkId, and AiChatViewModel assigns response.Sources without remapping. Fix: label evidence ONLY as SOURCE_1..SOURCE_N in the prompt (do not show internal ChunkIds to the model). Keep a per-message dictionary SOURCE_n -> DocumentChunk (and per-page record). After parsing, resolve each returned sourceId through that dictionary. Drop citations with unknown IDs. Fill in AiSource.PageIndex/PageNumber/WordRange/PdfCoordinates from the resolved chunk, NOT from model-supplied page numbers.
2. Quote validation. Normalize whitespace/case/hyphenation and check the model's quote against the cited chunk's text. If it does not match, do not highlight the whole chunk as if it were the quote; either repair by locating the best matching word range inside that chunk, or show the source button with a "location approximate" state. Never fall back to fuzzy-searching the entire PDF.
3. Retrieval depth is wrong: RetrieveAsync is called with _genConfig.MaxTokens / 500 (=4 chunks at the default). Add a separate configurable TopK (default 8) and an evidence character budget (default ~12,000 chars) so the prompt stays bounded regardless of output token setting. gpt-oss:120b-cloud has a large context window, but do not dump the PDF; retrieval remains required.
4. ClearForDocumentSwitch has no callers. Wire it (or better: per-document chat state) into tab switch, tab close, and document close, so chat, index, and the AI highlight never leak between PDFs. Keep chat history per document if practical.
5. Highlight precision: HighlightAiSourceOnPage draws the whole chunk's bounding box and always uses chunk.PageIndex (first page). Instead: use the resolved per-page record for the CITED page, compute ONE bounding rectangle from the words of the quoted range on that page (union of word boxes), and draw exactly one rectangle tagged "AiSourceHighlight". If the quote can't be located within the cited chunk, show the "Source could not be located" status instead of highlighting the entire chunk.
6. Navigation/waiting: after selecting the page, wait until the target page's canvas exists (retry with short delays up to ~2 seconds, or hook the viewer's page-rendered event) before drawing. This must work in Continuous view for far-away pages (e.g., page 743) and use ActiveViewer in split view.
7. Coordinate conversion: DrawAiSourceHighlight reopens the PDF with PdfPig on every click and ignores page rotation and CropBox origin. Cache page size/rotation/crop in the index (or a small cache) and convert PDF-space to viewer-space using Avalanche's existing conversion, including rotation and CropBox offset.
8. Multi-page chunks: the chunk stores WordRanges/PdfCoordinates per page. Make sure each source record maps to exactly one page.
9. ChatMessage is a plain class mutated after being added to the collection. Make sure the UI actually updates when Content/Sources/IsLoading/Error change (INotifyPropertyChanged or replace the item).
10. OCR: DocumentIndexer has no OCR path. If a page has no usable text layer, surface "This document has no text layer" in the AI panel. If reusing Avalanche's existing OCR service is straightforward, do it; otherwise leave a clear TODO and the message.

4. PROMPT TO THE MODEL (rewrite BuildSystemPrompt)
==================================================

System message: answer only from the supplied evidence; if insufficient, say so; distinguish the author's claims from your own explanation; cite only the given SOURCE_n IDs; never invent IDs, page numbers or quotes; quotes must be copied exactly from the cited source; prefer several supporting sources; do not cite passages merely because they share words. Output ONLY a JSON object:
{"answer": "<markdown>", "sources": [{"sourceId": "SOURCE_2", "quote": "<exact text from that source>", "reason": "<why it supports the answer>"}]}
(Do not ask the model for page numbers; the app derives them from sourceId.)

Evidence format:
[SOURCE_1] Page 147 (section: ...)
<text>

Include the last N chat turns (bounded, e.g. 6 messages) plus the current question. Retrieval runs on every new question; for short follow-ups like "why does he think that?", rewrite the retrieval query by prepending the previous user question so retrieval has context.
